# Critiques: Hard boundaries

Five critics attacked [the Hard boundaries proposal](../proposals/packages.md), one lens each.

| Lens | Score |
| --- | --- |
| determinism | 5 |
| performance | 5 |
| extensibility | 5 |
| migration | 5 |
| simplicity | 4 |

## Determinism — 5/10

The vocabulary is right: name tables with formerNames, a stored WorldBase, sections parsed with looseObject defaults, exact math, an integer unitHash, named streams with no parent draws, commands stamped with ticks, section digests and a save-load-run property test. The migration story is where it fails, and several claims are false against the code. Steps 6, 7, 9 and 12 each change what is persisted, and each deploys to playdawnfolk.com on merge, yet the table says "saves: none". Nothing reads the intermediate shapes, so either saves from some builds break or every step quietly adds the per-version readers the owner rejects. Release A bundles generation changes, which break saves, with simulation changes, which break nothing. Players who don't open the game in the short window after step 3 get the land-changed dialog. The thing store and the field store drop state that today's saves keep: the free-slot order, the order of each active set, per-slot generations, and the kind index inside ThingRef. That breaks the proposal's own "save, load, run N equals run N" proof. The "visual-only presentation stream" is a trap: today's "visual" draws (ember durations) are game state. The exact-math list and the GritQL denylist miss functions the engine uses today. The lint is scoped by folder path, so it misses module root files that the simulation imports. Fixing these takes discipline (freeze the save schema first, refactor behind it, keep order canonical), not a different architecture.

### Strengths

- Name tables cover every catalog stored by index, each with an unknown-name policy (fallback or drop). formerNames handle renames, and OLDER_SAVE_PLANT_SPECIES stays frozen. There are no index remap tables per version.
- defineSaveSection runs safeParse and the loader keeps the parsed result. That fixes a real bug: today z.custom throws away the looseObject parse (saved-world.ts:116-118), so no defaults ever apply and code like `snapshot.volcanoes === undefined ? [] : …` (simulation.ts:322) has to exist.
- Saves stop depending on the generator: a stored WorldBase per world, saves pointing to {baseId, baseHash}, and old saves regenerated and checked once.
- Exact math as an fdlibm port with golden tests in several engines, the hypot-to-sqrt codemod, the order-free unitHash(seed, tick, cell, rule) for reaction chances, and named xoroshiro streams seeded by id with no parent draws, saved and re-derived when missing.
- Commands only, stamped with ticks: setViewFocus is removed, strokes, meteors and lake filling run on ticks, and tasks, tornadoes and jobs become data, so snapshot() never returns null. Speed, pause and the backlog move out of the simulation into a scheduler.
- Section digests fold into a root hash per turn, so a desync can be traced to a section. Field digests are cached per 64×64 chunk. The replay header carries the build, catalog hash, seed and base hash. The catalog hash is part of the lockstep handshake.
- Order lives in explicit lists (STEP_ORDER, REACTION_ORDER) checked by tests, and there is no topological sort.
- Field operations centralize the roughly 33 raw field writes (fire.ts, catastrophes.ts, volcanoes.ts, land-powers.ts, element-powers.ts, water-recomputation.ts). That is what makes dirty-chunk hashing trustworthy.
- Per-slot generations on ThingRef end the ABA reuse of plant slots.
- The event queue is typed, ordered and per tick, and the hasher sees it, instead of ad hoc fan-out. A fast-check save-load-run property and cross-engine replay CI are planned.

### Findings

- **high**: The migration table claims 'Hash / saves: none' for steps 6, 7, 9 and 12, but each changes the persisted shape and deploys on merge. Nothing reads the intermediate shapes, so either saves from some builds stop loading or each step adds a reader for the previous main shape. That is per-version migration under another name. 'Today's flat top-level keys become section keys, so old saves are already valid envelopes' is true only of the key names, not of who owns what is inside them.
  - Evidence: The save is {generationFingerprint, plantSpecies, request, simulation, summary, version} (saved-world.ts:120-129). simulation.world alone holds fields (crop, fire, heat, scorch, trodden, fuel sparse; snow and wetness dense), vegetation, terrain diffs, crossings, monumentConditions, occupancy, cropCodes and canopy fuel (world-state.ts:79-94, 222-258). In the target these belong to the field store, the thing store, WorldBase, crossings, monuments, buildings and farming. A field's values and its active set are split across keys: values in world.fields.fire and world.fields.heat, active order in simulation.fire.{burning, heated} (fire.ts:75). People live in society.people as objects, yet the sickness walkthrough needs them in the thing store with trait columns ('Per-person columns are saved by the thing store'), and that contradicts 'Moved as is: society internals'. In step 9 the volcano's Map<cell, heat> becomes a lava field. Step 12 splits society into tribes, jobs, construction and technology. The project merges 1,347 commits in a month (git log origin/main), so every intermediate shape reaches players.
  - Fix: Freeze the save schema first and refactor behind it. In step 3, define the target envelope and section schemas: one fields section with per-field values plus active order, one things section with per-kind columns, free lists, generations and name tables, and module sections. Write them from today's classes through adapters. Steps 6 to 12 then swap implementations without changing the bytes on disk. Read the pre-envelope v1 shape through one frozen adapter that is never extended, the same treatment OLDER_SAVE_PLANT_SPECIES gets. Later renames and splits go through name aliases (formerKeys on sections, formerNames on fields, traits and columns), not through version readers. Add a CI job that builds origin/main, creates and runs a world for 600 ticks, saves it, then loads that save on the branch and fails if any section reset.
- **high**: Hash release A mixes generation changes (exact math, unitHash and named streams in generation) with changes that are only simulation. Simulation-only changes affect no save and no player-visible seed, because no replays exist yet. Generation changes give every base-less save the land-changed dialog. Bases are attached only on a launch between step 3 and step 4, and with continuous deploy that window can be hours.
  - Evidence: Proposal step 4: 'saves never opened since step 3 get the land-changed dialog'. Loading regenerates from the seed (simulation-worker-api.ts loadWorld → generateUnsettled → restoreSavedWorld). The fingerprint was narrowed on purpose to the 6 saved layers 'so old saves keep their land' (commit 5d9d385). Shared seeds, the 'striking seed' content and the tests that pin worlds by seed all change on the same day.
  - Fix: Split release A. A-sim covers exact math, unitHash, named streams, ticks for strokes and lake filling, and lightning without the camera, all in the simulation. It breaks no save and can ship any time. A-gen covers the generation changes and ships only after step 5. It keeps a frozen copy of the generator from just before the change, as a self-contained package that is dynamically imported only when a save has no base. That copy regenerates the island, checks the fingerprint and attaches a base. Delete it after a published sunset date. Record a generatorVersion on each base and on shared seeds so a seed can still name its island.
- **high**: The thing store design drops state that today's saves keep and that decides future behavior: the free-slot order, per-slot generations, and the kind inside ThingRef. That last one is a dense index, which the proposal itself says is 'never saved', yet ThingRefs will sit inside saved jobs, tasks and claims. After a load, new things get different slots, slot-bucketed systems process different people each tick, and saved refs can point at the wrong kind.
  - Evidence: VegetationStore allocates from a LIFO free list, `this.#freeSlots.pop()` (vegetation-store.ts:556-561), and the snapshot saves freeSlots and nextInCell (lines 448-449). That is why loads are faithful today. The research brief recommends 'Derived links are not saved', and the proposal's thing store 'saves columns and types by name' with no mention of free lists or generations. The sickness walkthrough buckets by `slot mod 20`. claimedPlants holds plant slots (society.ts:86, 332). ThingRef { kind, slot, generation } with 'Dense indices are assigned at freeze time and never saved' (proposal §4) contradicts 'Jobs, tornadoes and tasks are data'.
  - Fix: Either save free lists and generations per kind, or make allocation canonical, always taking the lowest free slot, which is derivable from occupancy, and still save generations. Encode refs in saved state only through a thingRef codec that writes the kind name plus slot and generation. Add a test that fails if a section schema contains a raw ThingRef or a dense index field without a codec.
- **high**: Active-set order is part of the state, and the generic field store doesn't preserve it. Fire visits burning cells in insertion order, consumes random draws in that order (embers) and updates neighbors in place. A sparse field save that scans cells in ascending order rebuilds the set in a different order, so 'save, load, run N' diverges from 'run N'. That is the proposal's own proof property, and lockstep resync and replay keyframes depend on it.
  - Evidence: CellSet keeps insertion order, retain() compacts in order, and snapshot and restore keep that order (simulation/world/cell-set.ts). Fire iterates `#burning.retain(burnCell)` and then `#heated.retain` (fire.ts:161-166). #throwEmbers draws `tick.random.chance` in that order (fire.ts:325-334). #spreadHeat skips neighbors already burning this pass (fire.ts:297). sparseDifference scans cells in ascending order (sparse-values.ts:8-24). Proposal: `Field.active: CellSet` with `save: 'sparse'`, and nothing about order.
  - Fix: Make every active set iterate in ascending cell order, for example as a bitmap scanned by words, so order is a function of membership and never needs saving. That costs about 12.8k words per field per tick at 640². Make reactions order-free as well: draw chance from unitHash (already proposed), and read neighbor values from the previous tick (double-buffer or deltas applied at the end of the pass) instead of in-place updates. Ship that as a named hash change, not as 'unchanged'.
- **medium**: The 'unhashed presentation stream' for visual-only draws is a trap. Draws the code labels as visual today feed game state, so moving one onto an unhashed stream desyncs peers silently.
  - Evidence: hurlBurningDebris draws `durationSeconds = random.between(1.2, 3.2)` (catastrophes.ts:326), and the volcano bombs do the same (volcanoes.ts:373). EmberSystem copies `remainingSeconds: durationSeconds` (embers.ts:78), and that decides when and where the ember lands and ignites. Embers are saved (saved-world.ts snapshot `embers`). The determinism audit itself called these 'visual-only durations'.
  - Fix: Give the simulation no presentation stream at all. Anything visual-only is derived on the main thread in the presenter from hash(thing id, tick). If a value stays in the simulation, it is state and uses a hashed stream. Ban unseeded randomness in simulation code by closure (see the exact-math finding).
- **medium**: Derived caches that lag behind state are hidden state. Step 1's 'save-load-run equality' cannot pass on today's code, yet step 1 is labeled 'none'. The proposal adds more lazy caches (mover buckets 'rebuilt at a tick's first query', block counts, chunk digests) and has no rule against this class of bug.
  - Evidence: Navigation is rebuilt every 50 ticks in a live run (simulation.ts:46, 544-546) but at once on restore (simulation.ts:306). After a terrain edit, a run loaded mid-window walks on fresh navigation while the live run walks on stale navigation. footingChanges.takeRegion() (navigation.ts:59) reads a change tracker that is never saved. #hasSuddenHeightEdit is reset on restore (world-state.ts:300).
  - Fix: Rule: every derived structure is a pure function of saved state at each tick boundary, rebuilt at fixed tick points that are the same in both runs (for example, rebuild navigation in the tick that edits the terrain), or else it is saved. Change trackers that feed simulation decisions are saved. Frame trackers never feed the simulation. Key lazy indexes to tick.index so a query from the UI between ticks can't shift a rebuild. Move the fixes for these into step 1, or mark the step-1 property as expected to fail until step 4.
- **medium**: Step 6 claims 'hashes unchanged after each', but the proposed field semantics can't match today's code. Snapping below the floor on every write changes gameplay, not just hashes: heat from several weak sources can no longer add up past the floor. Maintaining active sets at once also reorders sets that today are trimmed lazily.
  - Evidence: addHeat accumulates without clamping (fire.ts:126). The floor, HEAT_FLOOR = 0.002, is applied once per pass after all burning cells have emitted (fire.ts:339-349). A young fire emits about 0.14×0.75×0.05×0.1 ≈ 0.0005 per neighbor per tick, so several contributions per tick must add up. Raw `fields.fire[cell] = 0` writes leave the cell in #burning until the next retain (land-powers.ts:204, water-recomputation.ts:412, catastrophes.ts:355). A re-ignition before then keeps the cell's old position, because add() is a no-op for members.
  - Fix: Apply floors in the field's own decay or settle pass, never in add or set. Either make the step-6 operations bit-compatible (lazy removal, insertion order kept) and prove it with the pinned hashes, or label the field-store PR as a named hash change. Don't claim both.
- **medium**: Exact-math coverage and enforcement have holes. The port list misses functions the engine uses today. The ban is a denylist. The lint is scoped by folder path, so shared module files the simulation imports are outside it.
  - Evidence: Calls outside tests: tanh at relief.ts:122 and 126, log2 at valleys.ts:160, river-chains.ts:100 and springs.ts:145. Fractional `**` (a pow) appears at island-layout.ts:435, 453 and 456, relief.ts:143, wetlands.ts:286 (`**=`), springs.ts:144 and water.ts:213. The proposal ports only 'sin cos atan2 exp log asin acos' and bans `Math.sin|cos|atan2|exp|log|pow|hypot` plus `**`, missing tanh, log2, asin, acos, tan, atan, cbrt, expm1, log1p and the hyperbolics. The tornado walkthrough's `tornado-path.ts`, 'pure path math, imported by both threads', sits in the module root, outside the linted `simulation/` folders.
  - Fix: Port pow, tanh and log2 as well. Enforce an allowlist: abs, ceil, floor, round, trunc, sign, min, max, sqrt, fround, imul and clz32. Check by closure, not path: extend the worker-closure test to scan every first-party module reachable from the simulation and generation entry (Vite or esbuild metafile) for any other Math member, Math.random, Date and performance. Turn on the cross-engine comparison in the same PR that lands exact math (see the CI finding).
- **medium**: Some saved state holds catalog indices that no name table reaches. The column and field schemas have no reference metadata and no baseline, so 'every catalog stored by index gets a table' can't be enforced, and the fuel encoding regresses.
  - Evidence: The tornado walkthrough writes `tornado.biome = sample.biome`, a dense biome index in a saved tornado. The sick trait's `illness` column is an index into illness rows, while ColumnDefinition is only {initial, name, type}. FieldDefinition.save is 'dense' | 'sparse' | 'derived', but fuel is saved today as a sparse difference against a value derived from the ground rule (world-state.ts:234), and canopy fuel against vegetation. The determinism-saves research asked for `baseline: zero|base|rule`, and the proposal drops it.
  - Fix: Add typed catalog reference codecs (biomeRef, groundRef, speciesRef, kindRef, thingRef, built on z.codec). Columns and fields declare `ref` and `baseline`. The envelope's name tables are collected from the codecs actually used, so a missing table becomes a type error instead of a forgotten list entry.
- **medium**: Section digests are written by hand, and the hot paths bypass the dirty tracking that the chunk cache relies on. Desyncs then go unnoticed until they spread to other state.
  - Evidence: `SaveSection.digest(hasher)` is written per section. The risks section keeps 'fire spread keeps a direct loop in its module', which writes raw arrays without Field operations, so chunks are never marked dirty. Nothing says how trait columns in the thing store are digested.
  - Fix: Default digest = a canonical structural hash of `write()`: keys in sorted order, typed arrays read as u32 words, NaN normalized or asserted absent. Only hot sections get incremental digests, and a CI test proves the incremental digest equals the structural one across a scripted 600-tick run. Any raw loop must touch the same dirty tracker, or its field is digested in full.
- **medium**: Pause and command-only steps are left undefined. The text says 'a paused world applies commands without running nature', but stepWorld always calls clock.next() and runs every system. If paused steps advance Tick.index, the calendar day moves while paused. If they don't, several stamped commands share one tick and nothing orders them, because StampedCommand has no sequence number.
  - Evidence: Proposal §4 stepWorld vs §9 'Commands only'. StampedCommand is {tick, player, kind, payload}. Today strokes and tasks run on real seconds before the ticks, even while paused (simulation.ts:505-509).
  - Fix: Define an intake-only step that applies commands under the key (tick, sequence) without advancing the clock. Sort commands canonically by (tick, player, sequence) inside the worker, which also does the stamping. Record intake-only steps in replays and digest them. Have stroke commands carry their sample polyline with integer milliseconds, so brush strength doesn't depend on speed or how ticks are batched.
- **medium**: Absolute pinned hashes won't survive 30 to 100 agent PRs a day, and the cross-engine check only arrives in step 13. Any tuning PR changes the 600-tick hash, agents will re-pin by reflex, and determinism regressions such as a new Math.sin or an inconsistent sort comparator will pile up unseen for months after release A.
  - Evidence: Step 1 pins layer hashes and 600-tick hashes, and step 13 adds 'Cross-browser replay CI'. Simulation code sorts with comparators in settlement.ts:59 and 194, prospecting.ts:50, raids.ts:95 and raid-campaigns.ts:284. A comparator that is inconsistent or meets NaN orders differently in V8's TimSort and the merge sorts of JSC and SpiderMonkey.
  - Fix: Make determinism CI differential, not pinned. On the same commit, require Node (V8), Bun (JSC), Firefox and WebKit to agree, and require 'save at N/2, load, run' to equal 'run N'. Turn it on with release A-sim. Pin absolute hashes only for PRs labeled hash-neutral: CI computes the base commit's section digests and requires equality, and reports which sections changed otherwise. Add a sortBy helper that always breaks ties by id.
- **low**: Some orders come from the alphabetical roster, so renaming or adding a module changes float results elsewhere. That contradicts 'hashes unchanged per move' in step 12.
  - Evidence: 'listeners run in roster order', roster lines are 'one sorted line each', stats.effective applies 'registered modifiers', cells.tagged('wet') returns fields in freeze order, and dense indices are assigned in manifest order. Float multiplication and addition aren't associative, so base×a×b can differ from base×b×a.
  - Fix: Put every order that affects simulation in a pinned list (STEP_ORDER, REACTION_ORDER, plus LISTENER_ORDER and MODIFIER_ORDER), or sort by a stable id with code-unit comparison. Add a rule that a listener writes only its own module's state, so its order stops mattering.
- **low**: Attaching a base trusts a fingerprint that is deliberately weak. For saves without a fingerprint it trusts a river heuristic. Attaching freezes whatever the current generator produces, permanently.
  - Evidence: The fingerprint covers only baseTemperature, carving, ground, height, riverStrength and waterSurface (5d9d385), not biome, moisture, dryness, variation, woodland, coastDistance, monuments, deposits or springs. A null fingerprint falls back to doRiversFollowTerrain (saved-world.ts:206-212). monumentConditions are applied by position (world-state.ts:284-286).
  - Fix: Attach automatically only when a non-null fingerprint matches. Store provenance ('created' or 'attached', plus the generator build). For saves without a fingerprint, keep regenerating on every load as today until the player confirms the land. Write the base and the save in one IndexedDB transaction across both stores, and remove a base when no save references it.
- **low**: When a section fails to parse it resets silently, and the reset is coarse. One bad column wipes every plant, and a reset during a lockstep resync is a desync nobody sees.
  - Evidence: In defineSaveSection, failure means `section.reset()` and the status 'reset'. The thing store saves every kind's columns in one section.
  - Fix: Apply defaults per column and per field (a missing column takes the trait's initial value, unknown columns are dropped, renamed ones resolve through formerNames). Show players a load report when anything reset. Treat any reset as fatal in resync and replay mode.
- **low**: A 32-bit tag mask overflows without any error once modules and mods register more than 32 tags or traits, and the overflow changes query results in unrelated modules.
  - Evidence: `ThingFilter { kinds: number; tags: number; traits: number; excluded: number }` holds 'a Uint32Array mask per type'. In JS, `1 << 32 === 1`, so tag 32 aliases tag 0.
  - Fix: Use multi-word masks (Uint32Array words per filter), sized at freeze time. Freezing fails if any bit index would exceed the capacity.

### Worth grafting

- Name tables for every catalog stored by index, each with an unknown-name policy (fallback or drop), formerNames on rows, and the legacy default order (OLDER_SAVE_PLANT_SPECIES) frozen and never extended. No per-version index remaps.
- defineSaveSection: schema safeParse, z.looseObject with field defaults, and the loader keeps the parsed output, replacing today's z.custom wrapper that throws the output away.
- A WorldBase per world in its own IndexedDB store, with saves referencing {baseId, baseHash}. Old saves are regenerated, checked and given a base once, so later generator work no longer threatens saves.
- Exact math in the kernel as an fdlibm-style port, pinned by golden tests in V8, JSC and SpiderMonkey, plus the hypot-to-sqrt codemod.
- An integer unitHash(seed, tick, cell, ruleHash) gives reactions an order-free chance. Named xoroshiro streams are seeded from lowbias32(worldSeed ^ fnv1a32(id)) with no parent draws, saved in randomStreams and re-derived when missing.
- Commands are the only input, stamped with ticks. setViewFocus is removed, lightning picks a seeded site, strokes, meteors and lake filling run on ticks, and tasks, tornadoes and jobs are data, so snapshot() never returns null.
- Speed, pause, the backlog and the 40-tick cap live in a scheduler outside the simulation, so the simulation is just step(commands).
- Section digests fold into a root hash per lockstep turn, with field digests cached per 64×64 chunk. Replay header: build, catalog hash, seed, base hash and names. The catalog hash is part of the lockstep handshake.
- Field operations as the single write path for cell fields, which makes dirty-chunk hashing and frame marking reliable (floors move to the decay pass).
- Per-slot generations on ThingRef, against ABA reuse of slots.
- Explicit pinned order lists (STEP_ORDER, REACTION_ORDER) whose completeness tests check. No topological sort.
- A typed, ordered, per-tick event queue that the hasher sees, with a depth cap, instead of ad hoc fan-out between modules.
- The fast-check 'save, load, run N equals run N' property, and replaying seeds 3, 7 and 11 for 600 ticks across Chromium, Firefox, WebKit and Bun.
- No SharedArrayBuffer, the pull model with one advance in flight, and the lockstep socket inside the worker so React stalls never delay ticks.
- The chronicle and notices carry message ids with values instead of English text, which fixes both localization and save stability.

## Performance — 5/10

The query layer holds up on performance. It is allocation-free, takes compiled filters, writes into caller buffers and uses grid indexes, and I measured the tornado at 0.4 µs (r=45 m) and 3.1 µs (r=140 m). The new generic machinery around it has no cost model, though. Reactions driven by dense fields, a root hash every tick, a method wrapper on every field write, trait responses with no stated driver, closure-based stat modifiers, a full-island fireDistance rebuild, per-field frame sections and per-module terrain textures could each use up most of the worker's tick budget at speed 16 (160 ticks/s, about 6.25 ms per tick) or hit a hard limit on the main thread. Only the query API gets a bench gate (step 7). All of this can be fixed by adding contracts: sparse drivers only, a sweep cadence for dense rules, cell-driven responses, a hash only at turn boundaries with dirty pages, packed presented fields, shared field textures, and budgets in a nightly bench. Until those are in the plan, the stance makes the slow path the easy path. Numbers come from Node 24.22.1 on this Mac; the scripts are in /private/tmp/claude-501/-Users-svidskiy-Developer-svidskiy-dawnfolk/f224a3c7-cf6b-4066-884d-19a8c99c1ec2/scratchpad/architecture/critic-perf/ (bench.mjs, misc-bench.mjs, exp-bench.mjs).

### Strengths

- The query API is allocation-free, with compiled filters, separate verbs (count, any, nearest, collect, visit), out-params and squared distances. My bench agrees with the proposal's claim of about 1 µs at the default radius: summarize at r=45 m took 0.4 µs and at r=140 m took 3.1 µs, covering fields and plant type counts over 512k plants.
- It keeps typed arrays and an in-house store and rejects ECS libraries. That matches the research numbers: 10–18× less memory per entity and 150–490× faster spawn and despawn.
- Movers go into 40 m counting-sort buckets rebuilt once per tick (22 µs for 5k), replacing O(n²) scans like engagement.ts:33 and Obstacles.near on every mover step.
- It admits that fire spread keeps its direct loop and puts the generic visitor behind a bench gate in step 7.
- It keeps the pull model, transferables and no SharedArrayBuffer, and the bridge it proposes in place of Comlink drops a UUID-keyed RPC layer.
- The hypot-to-sqrt codemod is a speedup. Exact math is cheap: my fdlibm exp port ran at 10.4 ns against 3.1 ns for Math.exp in V8 (6.8 against 2.4 ns in JSC), and in JSC Math.exp differed from the port on 9.9% of 100k inputs, so the change is needed.
- Dropping react-markdown and remark-gfm removes a 50 kB gz chunk that Workbox precaches for every player. zod/mini saves about 19 kB gz per chunk.
- A WorldBase in IndexedDB lets a load skip regenerating the island (seconds) in favour of reading and gunzipping about 16 MB, which is a startup win.

### Findings

- **high**: Reactions can be driven by a dense field, and that walks the whole island every tick. Wetness is declared floor 0 and save 'dense'. Water cells are pinned at wetness 1 (surface.ts updateWaterCell), so wetness's active set never empties. After rain it covers all land. Walkthrough D's 'germs grow on cells tagged wet' can only be driven by wetness. The pass also makes one walk per reaction, calls a when closure and an apply closure per cell, and computes a unitHash for every cell that passes, needed or not.
  - Evidence: Bench (bench.mjs §2): 3 reactions driven by wetness over 250k active cells took 4.76 ms per tick. At speed 16 that is 760 ms of worker time per second, above the whole budget of about 6.25 ms per tick. The same douse rule driven by the fire set (5k burning cells) took 27 µs, and 43 µs when it sums two fields tagged 'wet'. The proposal's Reaction signature passes `cells: Cells` to the closures, which invites a `cells.field(X)` lookup per cell.
  - Fix: Allow only sparse fields and exposures to drive a reaction, and have catalog freeze reject a dense driver. Rules that depend on dense conditions (germs on wet cells, acid bleaching) run on a row-sweep cadence like SurfaceSystem's 32 rows per tick, with their chance scaled by the sweep period. Fuse reactions that share a driver into one pass. Compute chance only when apply asks for it. Resolve field arrays at create time and pass raw arrays, not Cells.
- **high**: TraitResponse has no driver contract, and FLAMMABLE gives plants a per-plant 'burning' f32 column. If a response iterates the things that carry a trait and reads each one's cell, the flammable response touches all 512k plant slots every tick. Today fire is cell-driven: canopyFuel is a per-cell aggregate, and fire.ts calls vegetation.burnTreesInCell(cell) in #consumeFuel and #burnOut, so plants only flip state.
  - Evidence: Bench (bench.mjs §3): just the base-type lookup over 512k plants takes 0.33 ms. Adding the random-access read of fire[cell[p]] brings it to about 1–2 ms per tick, or 160–320 ms per second at speed 16. A per-plant burning value that decays also needs a per-tick walk of the burning plants. Plant capacity is 1.25 × cellCount (world-generator.ts:41), which is 737k slots at 768².
  - Fix: Specify drivers. For storages that live in cells (plants, fixed things), walk the driving field's active set and then each cell's thing list. Drive responses by thing only for movers and other kinds with counts in the thousands. Plants keep their burning state per cell (canopyFuel plus a state flip) and get no per-plant burning column. Add a bench budget per response.
- **high**: stepWorld returns hasher.digest(tick) on every tick. Section 9 caches field digests per 64×64 chunk, but gives the thing store (plant columns, 20 MB) no incremental scheme. Single-player pays for hashing even when nothing consumes the hash.
  - Evidence: Bench (bench.mjs §5): hashing the whole plant store (512k × 40 B) took 6.1 ms and 10 whole float fields at 640² took 4.9 ms; research/determinism-saves.md measured 5.6 ms. Rehashing a rain tick's 30 dirty field chunks costs 150 µs, which is fine. Without caching for things, a per-tick digest takes about 11 ms, more than the tick at any speed above about 9×.
  - Fix: Digest only at turn boundaries (the research suggests 2 ticks) and only when something consumes the hash: a lockstep peer, the replay recorder or a test. Hash thing columns per 4096-slot page, with dirty bits set by the store's write API. Rehash movers in full, since they are small. Budget 0.3 ms per turn in the bench.
- **medium**: Routing writes through Field.value/add/set (clamp, floor snap, active-set insert, frame row mark) costs 2.6× to 9× in the surface sweep, the hottest dense loop. It also rules out the tricks SurfaceSystem uses today: raw Uint32Array bit compares and skipping settled 32-cell segments with #isKnownSettled.
  - Evidence: Bench (bench.mjs §1), 20,480 cells × 2 fields per tick: raw writes 75 µs; Field methods with a single implementation 191 µs; the same call sites after seeing 4 Field classes (dense, sparse, derived, exposure) 672 µs. The repo already took a perf commit for a closure in a hot loop: 146c9b4 'pick detail levels with a loop instead of a closure'.
  - Fix: Use one concrete Field class with the storage policy as data and no subclasses, so call sites stay monomorphic. The owning module gets the raw `values` Float32Array plus bulk `markRows(first, last)` and `markSegment`. Keep the method API for sparse writes from other modules. summarize and reactions read raw arrays.
- **medium**: The plan has no packing contract for field frame sections, and no rule for which fields WorldReader exposes on the main thread. Today the 4 surface fields go as bytes in one row buffer, diffed against what was sent. A generic per-field section (float rows or sparse cell-and-value pairs) multiplies frame bytes. Making WorldReader.sample return heat, fuel, lava and temperature on the main thread forces fields the mirror does not hold today.
  - Evidence: frame-packing.ts packChangedSurfaceRows packs 4 B per cell for all four fields. world-mirror.ts:123 holds only `surface: Uint8Array`. Rain at speed 16 and 60 fps changes about 86 rows per frame: 220 KB today, 440 KB as float rows for 2 fields, 880 KB as sparse pairs. At the 40-tick cap the whole island changes: 1.6 MB today against 3.3–6.6 MB. All of it is freshly allocated buffers, copied on the main thread and uploaded to textures.
  - Fix: Add `presented: { channel, encode: 'byte' } | null` to FieldDefinition. Pack presented fields into shared RGBA8 row pages, diffed against what was sent, as today. Non-presented fields (heat, fuel, germs) never leave the worker. Split CellSample, which runs in the worker over all fields, from ViewSample, which runs in the mirror over presented fields only. Add a frame-bytes budget to the bench.
- **medium**: Terrain layers contributed by modules, each with its own data texture, run into the WebGPU sampled-texture limit. They also add a per-fragment sample over the whole island and a full-texture upload whenever their field changes.
  - Evidence: terrain-material.ts and its helpers sample about 13 textures: height, patchSteps, wetland, shore, surface, groundAlbedo, lava, fords cells and segments, outline, the field plan, the ground-warp target and fire glow, plus the shadow map. create-graphics.ts:40 passes no requiredLimits, so the device keeps the default of 16 sampled textures per shader stage. Walkthrough B adds 'a TerrainLayer tint from an acidity data texture'. terrain-textures.ts:128 sets surface.needsUpdate, which re-uploads the whole texture.
  - Fix: Use cell-state texture pages. Each presented field gets a channel in a shared RGBA8 texture (4 per texture), assigned at roster freeze. A TerrainLayer receives a channel node, not a texture, and uploads cover row ranges. Compile every roster layer in from the start and gate it with a uniform, so a field appearing mid-game never triggers a pipeline compile.
- **medium**: summarize and fireDistance are cheap for one tornado but invite per-agent or per-tick use with no throttle or budget. summarize fills every field (biome shares, slope with sqrt, type counts, tribe counts, movers) on every call. The proposal lists fireDistance with no build strategy; the research says 'lazily rebuilt per tick'.
  - Evidence: Bench: 5,000 agents each calling summarize at r=30 m took 3.2 ms per tick (500 ms per second at speed 16). A full chamfer rebuild of fireDistance at 640² took 2.7 ms (misc-bench.mjs), or 430 ms per second at speed 16 while anything burns.
  - Fix: Give summarize a request mask compiled like a filter, plus a per-tick memo keyed by cell and radius. Provide a kernel throttle such as everyNthTick(slot, n) and require it for per-agent area queries. Build fireDistance as a BFS from burning cells capped at the largest query radius, or as a minimum distance per 16×16 block, rebuilt only when the burning set changed. Add a budget per query.
- **medium**: stats.effective applies a list of closure modifiers on every call, and the same path can also explain itself to the inspector. That is fine for 600 plants and ruinous in any pass over all plants, or over every person if sickness spreads.
  - Evidence: Bench (bench.mjs §3): 600 plants took 15 µs, which is fine for the tornado. All 512k plants took 13.5 ms, against 0.33 ms for the base lookup (40×).
  - Fix: Fold modifiers that depend only on type and global state (technology, season, rules) into a per-type Float32Array per stat, refreshed when those change. Limit per-instance modifiers to column reads compiled into the stat. Give explain() its own path, used only by the inspector.
- **medium**: Every Field carries a CellSet active set, which is mostly overhead for dense fields, and the field count is about to grow (lava, acidity, germs, exposures).
  - Evidence: cell-set.ts allocates an Int32Array plus a Uint8Array per cell: 2.81 MB per field at 768², next to 2.25 MB of values. About 11 fields plus 2 exposures need about 37 MB of active sets and 29 MB of values in the worker, before hash-chunk caches. Wetness and snow have nearly every cell active.
  - Fix: Give only sparse fields and exposures active sets. Dense fields use bitsets over 32-cell segments, as SurfaceSystem.#isKnownSettled does today (about 2.3 KB per field), for dirty and settled tracking.
- **medium**: impact.apply emits thingHarmed for every harmed thing on every tick. Payloads are objects, so the 'preallocated' queue still allocates, the hasher digests every event, and presented events are structured-cloned into frames.
  - Evidence: 200 people in a burning camp produce 200 events per tick, about 540 per frame at speed 16. That is far past the guideline of cloning about 10 KiB per frame cited in research/worker-bridge.md. Emitting alone is cheap: 300 emits took 1.8 µs. The cost is in fan-out, hashing and cloning.
  - Fix: Have impact accumulate into columns (harmThisTick, lastCause) and emit events only for state changes such as thingKilled. Keep event payloads in a typed ring buffer (kind plus 4 numeric slots) and build objects only for presentation. Coalesce presented events per frame by kind and area. Add a test for the per-tick event budget.
- **medium**: Step 3 attaches a base to every stored save in the background on first launch. That regenerates each stored world through the full pipeline, including erosion and hydrology, on the single simulation worker while the player plays, and then gzips about 16 MB per world.
  - Evidence: Section 14, step 3. The worker API runs generation and advance on one worker (workers/simulation-worker-api.ts). Each regeneration takes seconds on a laptop and more on phones, and every advance stalls behind it.
  - Fix: Attach a base lazily when a save is next loaded, since loading regenerates the island anyway. Otherwise use a separate short-lived worker at idle, one world at a time, after checking navigator.storage.estimate().
- **low**: Mover buckets are 'rebuilt at a tick's first query', but impact pushes, hand drops and life-phase movement change positions within the tick. If a write sets a dirty flag that forces a rebuild at the next query, rebuilds happen per query. If not, queries see stale buckets.
  - Evidence: A rebuild costs 22 µs for 5k movers. Interleaving thousands of moves and queries in the life phase would cost tens of ms per tick.
  - Fix: Rebuild once per phase boundary (emit, life). Pad the query radius by maxSpeed × tickSeconds and test exact distance on live positions. Teleports update their bucket in place. No write ever forces a rebuild.
- **low**: The tornado's cost claim (about 1 µs, 'two block walks') credits block counts that do not apply at tornado radii, and it leaves out the uproot visit and impact.
  - Evidence: Blocks are 16×16 cells (160 m). At r=45–140 m almost no block lies fully inside the disc, so type counts come from scanning edge cells. Summarize alone is 0.4–3.1 µs (measured). Stats.effective over 600 visited plants adds 15 µs, before the swirl stamp and impact. A realistic total is 5–25 µs per tornado per tick, still under 0.5% of a tick at speed 16.
  - Fix: Correct the numbers. Keep block counts only for queries of r≥300 m (camp siting, seed trees), or defer them until such a query exists.
- **low**: ThingVisitor.visit(thing: ThingRef, …) passes an object per visit. The store either allocates one per visited thing or reuses a mutable ref that a visitor can keep or queue (things.disturb), which causes aliasing bugs. The tornado code also builds an options object per uprooted plant.
  - Evidence: research/spatial-queries.md specified visit(kind, id, distanceSquared). The proposal changed this to ThingRef.
  - Fix: Pass numbers: visit(kind, slot, distanceSquared). Check the generation inside the store. If a ref has to be stored, pack it into one integer.
- **low**: ThingFilter stores kinds, tags, traits and excluded as single 32-bit numbers, which caps each at 32. The proposal already names about 20 tags, and mods will pass the cap. Changing the mask width later touches every filter test and the block-count channel layout.
  - Evidence: Section 4: 'Tags compile into a Uint32Array mask per type'. ThingFilter fields are typed `number`.
  - Fix: Use 2-word masks from the start, or assert the cap at freeze and keep field tags (strings resolved at create time) separate from thing tags.
- **low**: Complete, static rosters and per-module .po catalogs undo today's lazy loading. Package entry points and sideEffects are unspecified, and the closure test checks only which libraries the worker reaches, not chunk sizes.
  - Evidence: Today the start screen lazy-loads the engine and HUD (app/engine-launcher.ts:22,26; app/app.tsx:12). An INTERFACE_ROSTER that satisfies every module id puts every panel, icon and locale into the HUD chunk. Rollup keeps top-level define*() calls in barrels unless sideEffects is false.
  - Fix: Panel entries carry load: () => import(...), and Lingui catalogs load per language. Packages expose subpath exports with no root barrel and set "sideEffects": false. Add a chunk-size budget test for the start, engine, HUD and worker chunks next to the closure test.
- **low**: The bundle numbers are overstated: '37 kB gzip less in both the main and worker bundles'.
  - Evidence: research/packages.md: the command union is 25.4 kB gz with zod and 6.5 kB with zod/mini per chunk, about 19 kB each and about 37 kB summed over two chunks. Lingui adds 10.2 kB gz back to main (measured).
  - Fix: State about 19 kB gz per chunk and about 9 kB net on main after Lingui. Never parse event payload schemas in the worker's hot path.

### Worth grafting

- Keep the allocation-free query API: compiled filters, separate verbs, caller-owned out buffers, squared distances and numeric visitor arguments (kind, slot, distanceSquared).
- Only sparse fields or exposures may drive a reaction, and catalog freeze enforces it. Rules with dense conditions run on a row-sweep cadence (like SurfaceSystem's 32 rows per tick) with chance scaled by the period. Reactions that share a driver run in one fused pass, with chance computed only on demand.
- Trait responses are cell-driven for storages that live in cells (plants, fixed things) and thing-driven only for movers. Plants keep their burning state as a per-cell aggregate.
- Hash only at turn boundaries and only when something consumes the hash. Field chunks of 64×64 and thing-column pages of 4096 slots carry dirty bits.
- One concrete Field class with the storage policy as data. Owning modules get raw arrays and bulk row or segment marks; the method API serves sparse writes from other modules.
- Active sets for sparse fields only. Dense fields use 32-cell segment bitsets.
- A presented-field contract: byte-encoded channels packed into shared RGBA8 row pages that feed both the frame diff and the GPU textures. Non-presented fields stay in the worker. ViewSample on the main thread is separate from CellSample in the worker.
- Terrain layers receive a channel in a shared cell-state texture, not their own texture, so the default limit of 16 sampled textures is not reached. Every roster layer is compiled in from the start and gated by a uniform.
- Fold stat modifiers into per-type arrays. Per-instance modifiers stay as compiled column reads, and explain() is used only by the inspector.
- Summarize takes a request mask. Per-agent area queries must go through a kernel throttle. fireDistance is a bounded BFS from burning cells, or block minima, rebuilt only when the burning set changes.
- impact accumulates harm into columns and emits only state-change events. Event payloads use a typed ring buffer, and presented events are coalesced per frame.
- Mover buckets are rebuilt once per phase boundary, with the query radius padded by maxSpeed × tick and the exact test run on live positions.
- A nightly bench project with budgets (Vitest bench on tinybench): one tick at 640² and 768² with 500k plants and 5k agents, the reaction pass, the field sweep, frame build time and frame bytes, summarize and nearest, the hash per turn, and chunk sizes. Gate steps 6, 7 and 9 on it, not just step 7.
- Attach a WorldBase lazily when a save is next loaded, not to every save at first launch. Loading from a stored base, instead of regenerating, is a startup win worth keeping.
- Keep the hypot-to-sqrt codemod, the removal of react-markdown and Comlink, zod/mini, and lazy loading of HUD panels and locale catalogs.

## Extensibility — 5/10

The module folder with four sides, the rosters checked with `satisfies`, catalog freezing and the field operations are a good skeleton. The extensibility claims break down once you leave the four walkthroughs, which were picked because they fit. Three things are closed: the property and query model hard-codes today's vocabulary (a fixed CellSample and AreaSummary, `fireDistance`, 32-bit masks, no species or dynamic-state filters); tribes have no properties; and society and fauna have no extension points. On top of that, the rule that modules never import each other is broken by the proposal's own examples (`TORNADO_HIT_CAMP`, `RESISTANCE`, `floats`). I tested two new scenarios. Beavers that dam rivers need about 13–17 edits outside the module folder, spread over catalog, models, world/hydrology, fauna, life-powers and 6 roster files. Plague spreading through trade needs about 15–19 edits outside the two module folders, 4–6 of them inside society. Neither is close to "one folder plus roster lines". The tornado walkthrough also silently drops the swirl behavior, and its filter cannot actually affect buildings.

### Strengths

- The code is concrete and typed: System, Field, Reaction, ThingFilter, ModuleRuntime and SaveSection are all written out, so each claim can be checked.
- Modules are folders with manifest, simulation, engine and interface sides. Shared files like `tornado-path.ts` are imported by both threads, which fits the worker/main split well.
- The rosters use `satisfies { [Id in ModuleId]: ... }`, so tsc names a missing registration instead of a glob silently skipping it.
- The catalog is frozen in rounds (base, then modules, then scenario or mod), with dense indices assigned at freeze time and never saved. This is the right base for mods and for name-table saves.
- Field operations (clamp, floor snap, active set, frame marking) remove the per-pair writes, and the tag-driven douse rule really does give acid-puts-out-fire without new code.
- Frame and mirror sections are keyed per module, with a test that both key sets match. That fixes today's three edits per frame field.
- The 'Against the stance' notes are honest: one workspace for all modules, no premature traits in catalog, and a typed event queue instead of an untyped bus.
- `bun run new-module` writes the boilerplate, and a test checks it against the template.

### Findings

- **high**: The property and query model is closed: CellSample and AreaSummary are fixed structs of today's fields, and the query layer bakes in game rules. A field added by a module (acidity, germs, ice) cannot be sampled or summarized without editing the `world` and `simulation` packages. This contradicts principle 2 (vocabulary is data) and principle 4 (the kernel owns no game rules).
  - Evidence: The proposal's CellSample (world/reader/cell-sample.ts) lists fixed fields fire, heat, wetness, snow, fuel and lava. AreaSummary has fixed maxFire, burningCells, meanHeat, people, animals and buildings. Query has a fire-only `fireDistance(cell)`, and Cells has the vegetation concept `markDisturbed`. Walkthrough B adds `acidity`, yet nothing in the query API can report it. An ice-sheet module would need to edit CellSample, AreaSummary and the world walkability predicates. queries.md already counts 9 different water predicates in today's code.
  - Fix: Make samples index by field: `sample.fields: Float32Array` indexed by frozen field index, with typed accessors (`sample.value(FIRE)`). Compile summaries from a spec, e.g. `query.compileSummary({ fields: [{ field: FIRE, ops: ['max', 'count'] }], typeCounts: [PLANT_KIND], tagCounts: [TREE], tribes: true })`, filling a matching out-struct. Replace `fireDistance` with `distanceTo(fieldOrTag, cell)`. Move `markDisturbed` to the vegetation module as a field or exposure.
- **high**: Filters cannot express per-thing dynamic state. Tags are fixed per type and traits per kind, so 'sick people', 'burning huts', 'fleeing', 'adults' or 'carrying food' cannot be written as a ThingFilter. Walkthrough D depends on exactly such a filter.
  - Evidence: 'Tags compile into a Uint32Array mask per type' (proposal line 275). ThingFilterDefinition has only kinds, tags, traits, excludeTags and tribe. Walkthrough D calls `query.count(disc, SICK_PEOPLE)`, but `sick` is a trait applied to every `person`, so a trait filter matches all people. 'Held' is already special-cased in the live mask, which shows the gap.
  - Fix: Give every thing a `flags` column of module-registered state bits (sick, burning, fleeing, held, child), declared in manifests and assigned word and bit at freeze. Filters get `flagsAll` and `flagsNone` masks, and the bucket and plant indexes test them inline. Separately, add an allocation-free numeric predicate hook for rare cases, e.g. `where: ColumnPredicate` (column, operator, value).
- **high**: Future tribe systems have no extension points, and walkthrough D hides the edits outside its folder. There is no tribe entity with properties, and a module cannot add traits to the `person` kind it does not own. Society, with its closed job union, decisions, Stock and Tribe record, stays a monolith until 'later'. Diplomacy, beliefs, sickness and trade therefore all edit society.
  - Evidence: `JobKind` is a closed union of 28 kinds plus JOB_LABELS (src/simulation/society/jobs/job.ts:17-60). `Person` holds an object `job`, `carrying`, `weapon` and `name`, which don't fit the f32/u8 columns. `Tribe` holds `claimedPlants: Set<number>`, `fields: Field[]` and `stock` (tribe.ts). ThingKindDefinition.traits is fixed in the kind's own definition. Walkthrough D: 'Warmth, hunger and herbalism are modifiers other modules register', so society gains code for sickness. Risk section: society splits only after stat modifiers and events exist. My scenario, plague spreading through trade: a trade job needs a new JobKind plus decisions and work-planner edits; adding `sick` to person, registering modifiers and contaminating Stock each edit society; RESISTANCE and a goodsExchanged event go to catalog/elements; a market building and herbalism go to catalog/content; plus 6 roster files per module. That is about 15–19 edits outside the two folders.
  - Fix: Make 'society extension points' a migration step before deeper tribes: a `JobDefinition` registry (kind, labels, chooser consideration, step, save codec), need and consideration registries for decisions, and `extendKind(PERSON, use(SICK))` in manifests, resolved at catalog freeze. Add a first-class `TribeRef` with module-contributed tribe columns and stats, plus a relation matrix (allied, hostile, trades-with) readable through `query.tribes`. Allow side tables keyed by ThingRef for non-numeric per-thing data.
- **high**: The rule that modules never import each other is contradicted by the proposal's own walkthroughs. Every cross-module interaction therefore either breaks the rule or adds a central edit to catalog/elements, which turns catalog into the shared file every feature touches.
  - Evidence: TORNADO_HIT_CAMP is emitted by the tornado module and handled by a listener in `society` (lines 559, 619), but a module simulation side may import only its own manifest. RESISTANCE (walkthrough D) must be visible to society for it to register modifiers. Walkthrough C says 'the hand ... floats lets it be set on water' while 'floats stays private' to the boat module (Against the stance 3).
  - Fix: Define a small set of generic standard events in catalog with a `cause` name (`campStruck`, `thingHarmed`, `thingKilled`, `goodsExchanged`). Modules may listen only to catalog events or their own. Use pull-style modifiers: the consumer (sickness) derives RESISTANCE from stats that providers publish (warmth, hunger, technology), so providers never write code for consumers. Express hand placement as trait parameters, e.g. `use(GRABBABLE, { settlesOn: 'water' })`, so the hand never needs to know `floats`.
- **medium**: The filter vocabulary is too narrow and loosely typed for 'trees by species', rival gods and mods. Masks are single 32-bit numbers, filter definitions use strings, there is no `types` field, and tribe is a single number with a `-1` sentinel.
  - Evidence: ThingFilter has `tags: number`, `traits: number` and `kinds: number`, which caps the whole game, its modules and mods at 32 tags and 32 traits. Tag candidates already approach 32: tree, shrub, wooded, uprootable, anchored, wooden, craft, monument, crop, edible, predator, prey, small-game, grazer, the building roles, heat-source and others. Filters are written as `tags: ['uprootable']` and lookups as `catalog.plants.index('oak')`, so a typo silently matches nothing. 'Nearest oak' or 'nearest granary of my tribe' cannot be written because there is no types filter. `typeCounts` doesn't say which kind's index space it uses. 'People of hostile tribes' or 'tribes of player 2' cannot be expressed.
  - Fix: Use multiword masks sized at freeze. Make filter definitions take typed refs from `defineTag`, `defineKind` and `defineType`, and give them a `thingFilter({...})` helper that fills defaults. Add a `types` mask, a `tribes` mask and a relation predicate (`relation: 'hostile' | 'allied' | 'own'`, relative to the issuer). Give each kind its own typeCounts row.
- **medium**: Walkthrough A drops current behavior and contradicts itself. The tornado swirl is lost, the swept filter excludes buildings it should damage, the uproot filter uses a tag while the plant store dispatches on traits, and the block counts are coarser than the tornado.
  - Evidence: Today's `whirl` (tornadoes.ts:180-198) moves people and animals tangentially and inward or outward, but `Impact.push` is a single number with no direction. The SWEPT filter has `excludeTags: ['anchored']`, so anchored buildings take no harm, while unanchored ones get pushed. Today buildings take 60/s over the full radius and people 0.45/s and animals 0.9/s in the core (tornadoes.ts:21-23, 132-135); one Impact has one area and one harm, and a single ARMOR scalar cannot express damage per cause. UPROOTABLE filters on the tag 'uprootable', but `disturb` dispatches on the `fellable` and `uprootable` traits (line 617), so trees are never visited unless they also carry that tag. Block counts cover 16×16 cells (160 m), while the tornado radius is 45–140 m (content/powers.ts:344). The '~1 µs' claim ignores the edge cells, which are almost all of them.
  - Fix: Split Impact by trait: `damageable` takes harm, `movable` takes motion, `frightened` takes fright, and each term has its own area and falloff. Add damage types (wind, fire, crush, cold, corrosion) with resistance stats per type. Take a `motion(thing, dx, dz, out)` callback so the swirl survives. Pick either tags or traits for felling and uprooting, not both. Define summaries as exact: whole blocks from counts, edge cells from per-cell lists.
- **medium**: SimulationContext has no API for editing terrain or water, and hydrology and walkability accept no contributions. The quake, meteor, volcano cone, land powers, beaver dams and ice sheets have no path except editing the `world` package, which the proposal treats as a stable layer.
  - Evidence: Cells exposes only field, exposure, tagged, setGround and markDisturbed. Today terrain is edited by 8 functions on WorldState (terrain-editing.ts:89-305: raiseTerrain, swellCone, flattenTerrain, levelGround, smoothTerrain, carveCrater, shakeTerrain...). My scenario, beavers damming rivers: a beaver row goes into central catalog/content/animals.ts; fauna needs edits because species behavior is hard-coded branches (fauna.ts:124, 416; beast-instincts.ts:311, 657); models needs edits because ANIMAL_LOOKS is central (animal-models.ts, animal-appearance.ts, clips); world/water hydrology must learn about dams; life-powers needs a spawn power, because each species has one (powers.ts:413); then 6 roster files and tsconfig references. That is about 13–17 edits outside the module folder.
  - Fix: Add `terrain: TerrainEditor` to SimulationContext (raise, flatten, carve, setGround) that batches edits and schedules the hydrology rerun. Add a `waterBarrier` layer and footing contributors so dams and ice join the single `hasWater` and walkability rule declaratively. Add a fauna behavior registry keyed by species tag or trait, so a species row lists behavior ids contributed by modules. Let looks be contributed by modules. Generate spawn powers from species rows.
- **medium**: Each module fans out to many roster and config files, and the per-module file counts are understated. Order lists are semantic rather than sorted, so new entries pile up at phase boundaries and parallel agent PRs will conflict.
  - Evidence: Every module must appear in MANIFESTS, SIMULATION_ROSTER, ENGINE_ROSTER and INTERFACE_ROSTER, with `null` entries required by `satisfies`. On top come STEP_ORDER, REACTION_ORDER, POWER_ORDER and JOURNAL_ORDER as needed, the project references in the app tsconfig, and per-module Lingui catalog paths, which clash with 'no globs'. Each module also carries 4 tsconfig.json files. 'A stateless power needs about 6 files' is wrong: module.ts, 2 tsconfigs, handler, simulation-module, interface-module, icon and 2 .po files already make 10, and a sound cue brings it to about 14. Git treats insertions at the same place as a conflict, and the repo merges 30–100 PRs a day.
  - Fix: Let the manifest declare `sides: ['simulation', 'engine']` and type each roster over only the modules with that side, which removes the null lines. Keep order within a module, and pin only cross-module pairs that write the same field, in short per-phase files. Have `new-module` write the roster lines, references and locale entries. Measure the proposal's own fallback, one tsconfig per side type across all modules plus the closure test, against 80 projects before committing to it.
- **medium**: Walkthroughs B, C and D rest on `TraitResponse` and `things.disturb`, and neither is defined. It is unclear what triggers a response, which things it visits, in what order and at what cost, so the 'properties, not pairs' claim for things cannot be checked.
  - Evidence: TraitResponse appears only as `responses: readonly TraitResponse[]` (line 407) and in the walkthrough tables. Movers are indexed only in 40 m buckets, so a response 'standing on a corrosive or burning cell' has no per-cell mover index to drive it. `things.disturb` dispatches on plant traits inside the store, and its behavior for movers and buildings is unspecified.
  - Fix: Define `TraitResponse { id, trait, drivenBy: field | tag, phase, visit(thing, cell, value, tick) }`, driven by walking the field's active set against a per-cell thing index (head/next for movers, refreshed once per tick). Pin the visit order (cell row-major, then id) and give responses an order list like reactions.
- **low**: Boolean tags on fields leak meaning into every consumer of the tag. Acidity tagged `wet` will also feed germ growth, mud and plant growth wherever code reads `wet`, and the walkthroughs never say how values from several tagged fields combine (sum or max).
  - Evidence: ACIDITY has tags ['wet', 'corrosive']. Walkthrough D: 'germs grow on cells tagged wet'. Cells.tagged(tag) returns a list of fields and leaves the combining to each caller.
  - Fix: Declare weighted contributions per field, e.g. `contributes: { douses: 1, corrosive: 1 }`, and have consumers read them through `cells.sumTagged(tag, cell)` and `maxTagged`. Name tags by effect (douses, soaks-soil) rather than by substance (wet).
- **low**: The tornado, meteors and embers stay private module state rather than things, although the brief lists them as things with properties. Fauna, people, the inspector and the hand cannot ask 'is a tornado near' except through generic danger zones.
  - Evidence: The tornado manifest holds 'power definition, death cause, message ids, frame payload types', with no thingKind, and the tornado lives in `state.active`. The brief: 'things (… lava, tornadoes, meteors, embers) expose declared properties'.
  - Fix: Make tornadoes, meteors and embers kinds with `storage: 'transient'` and traits such as `hazard`, `windSource` and `heatSource`, so `query.nearest(area, HAZARDS)` and the inspector work without importing the tornado module.
- **low**: Engine and interface extension points do not cover overrides of looks or overlays that belong to another module. Acid rain's 'green streaks' must reach into the weather module's rain renderer, and a trade-route or plague overlay has no minimap slot.
  - Evidence: EngineModule has layers, terrainLayers, effects, things, audio, emitters and mirror; there is no precipitation-look slot. Rain is procedural on the GPU inside weather rendering. InterfaceModule has inspectorRows, panels and stores, with no minimap or overlay contributions.
  - Fix: Add named slots in the engine and interface packages (precipitationLooks, minimapOverlays, ambienceLayers) that the owning module renders and other modules contribute to through typed entries.
- **low**: Scenarios with goals and data-only mods have no supporting model. Goals have no metrics to refer to, and a power cannot be added without code, which a compile-time TS roster cannot load from a data pack.
  - Evidence: The catalog has a 'scenario or mod' round, but there is no goal or metric registry. Powers need a PowerHandler (code), and SIMULATION_ROSTER is a tsc-checked constant. `rules: RulesReader` is read-only. A scenario goal such as 'reach the bronze era with 50 people by day 100' needs tribe properties, which don't exist.

### Worth grafting

- Typed rosters keyed by ModuleId with `satisfies { readonly [Id in ModuleId]: X<Id> | null }`, iterated by one MODULES tuple and never by object key order, so tsc names every missing line.
- The `Impact` struct (area, cause, harm, fright, danger, push or swirl, filter) as the single 'harm things in an area' path. It replaces damageArea + scare + addZone in tornadoes, volcanoes and catastrophes.
- Field operations (add, scale and set with clamping, floor snap, active set and frame marks) as the only way to write cell state, removing the 39 manual mark calls.
- Unify fields and exposures: an exposure is a field with `save: "tick"`.
- Rule: any event, trait, tag or stat read by a second module lives in catalog. A trait stays private only while one module uses it, and gets promoted when a second reader appears.
- Generic standard events (e.g. `hazardStruckCamp { cause }`) rather than per-hazard events, so society listens once.
- A typed, ordered, per-tick event queue that the hasher sees, for chronicle fan-out (28 `chronicle.record` call sites verified), with events typed by phantom generics and not zod.
- `defineSaveSection` that erases the generic without `as`, looseObject sections with defaults, and old top-level save keys reused as section keys.
- Frame sections paired with mirror sections by key, plus a guard test that the key sets match.
- A worker-closure test that builds the worker bundle and fails if three, react or zustand is reachable.
- A GritQL ban on Math.sin/cos/atan2/exp/log/pow/hypot, `**`, Math.random, Date.now and performance.now in deterministic folders.
- Layer-level composite tsconfig projects (4-5) with include globs for module sides, plus a short sibling-module import test, instead of workspaces and per-side tsconfigs.
- One STEP_ORDER list (or a Record<Phase, SystemId[]>) as the single source of system order.
- CellSample and AreaSummary carry per-field arrays indexed by catalog dense index, so module-added fields such as acidity show up in queries automatically.
- Static UI data (icon URL, label ids) in the manifest, so a stateless power needs no interface side.
- A step-0 spike before any structural move, and hash-changing work batched into named minor releases.
- The package changes backed by measurements: drop react-markdown and remark-gfm, move to zod/mini (about 37 kB gz measured), replace Comlink with a small typed bridge, keep the 'don't add' list (ECS libraries, Nx, Turborepo, DI, event-bus libraries).
