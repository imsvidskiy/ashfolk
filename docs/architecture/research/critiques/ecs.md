# Critiques: ECS-first

Five critics attacked [the ECS-first proposal](../proposals/ecs.md), one lens each.

| Lens | Score |
| --- | --- |
| determinism | 6 |
| performance | 6 |
| extensibility | 5 |
| migration | 4 |
| simplicity | 4 |

## Determinism — 6/10

The determinism ideas are right, but several of the proposal's claims don't match the current code. It takes the research's best tools: named streams per system, a stateless unitHash, tasks and tornadoes saved as data, cameras kept out of the simulation, an envelope with name tables, a stored WorldBase, and section digests. Four problems undercut it. (1) It says the golden digest stays identical through steps 5–7, which the code contradicts: people are f64 objects but would move into f32 columns, person.id feeds hashToUnit, writes would go through generic clamp/snap setters, and plant search order changes. (2) Its typed-column model has nowhere to put jobs, routes, names or cached state, so saves stay as lossy as today. The 'save, load, run N == run N' test and lockstep resync both depend on fixing this. (3) Thing references and kind indices come from registry order and are never mapped by name. (4) The hasher's dirty tracking is not kept apart from the frame builder's change trackers, which can cause false desyncs and can also hide real ones. The migration table also says 'none' for save changes at steps that do change the save, and it covers only two of the ~20 legacy save keys. All of this can be fixed without dropping the design. As written, though, the plan would hit unexplained golden-digest changes during migration and sometimes scramble old saves.

### Strengths

- Each system has its own named stream seeded from (worldSeed, systemId) with no draws from a parent, and per-cell chance uses a stateless unitHash. Together these mean a new module no longer shifts other modules' random draws, which matters at 30–100 PRs a day.
- Tasks are data sorted by (tick, sequence), and the tornado becomes a saved kind. This removes today's `snapshot()` returning null whenever isBusy is true (simulation.ts:201-208, 272).
- Exposure fields and events are cleared at the end of each tick, so by construction a save never holds them.
- The save envelope has name tables, `formerNames` on each catalog entry and a per-catalog policy for unknown names. This meets the owner's 'no per-version remap tables' rule.
- Old saves are read with one frozen reader per legacy key, not one per version. Saves that mix legacy keys and new sections (written mid-migration) load without extra work.
- A WorldBase stored in its own IndexedDB store protects saves from generator changes (terrain realism v2, seed fixes), and the bump in step 10 is ordered after the base exists.
- Section digests, a cached hash per 64×64 chunk for fields, NaN normalization, and cross-engine CI that includes Bun (JSC) as a cheap second engine.
- Lightning stops using the camera's view focus, strokes become per-tick samples, and water filling counts ticks. These close the real-time and camera gaps found in the audit (simulation.ts:503-524).
- The lockstep socket lives inside the worker, and the handshake compares the build id, catalog hash and module list.
- Generation may import only core, never the kernel, so it can't take state from the runtime.

### Findings

- **high**: The claim that the golden digest stays identical through steps 5–7 is false as specified, so the hash would change with no explanation in the middle of the migration.
  - Evidence: (a) The Person fields are all JS numbers, i.e. f64 (src/simulation/society/person.ts:46-73), but ThingTable offers only f32/i32/u8 columns, and the walkthrough reads `table.f32(POSITION.x)`. Rounding positions, health and timers to f32 changes every later step. (b) Gameplay hashes on serial ids: `hashToUnit(person.id, FLANK_SALT)` (rivalry/engagement.ts:162), `hashToUnit(person.id, raid.id*…)` (responses.ts:52). The proposal replaces the id with ThingId = kind<<24|slot. (c) The generic setters 'clamp and snap values below a threshold to zero', but today's writes differ per site, e.g. `fields.fuel[cell] = Math.max(0, … )` with no snap (nature/fire.ts:224). (d) `nearestPlant` visits rings row-major (research/queries.md:31), so ties broken by the lowest order key on a radial pattern pick a different winner. (e) The step-0 digest hashes today's state layout, and steps 1, 5 and 6 change that layout, so the same digest can't even be computed afterwards.
  - Fix: Use f64 columns for everything that is a JS number today. Keep a saved `serial` column and hash on it, never on ThingId or slot. Make setter policies per field, with today's raw behavior as the default. Budget and label the digest bumps for step 7 the way step 8 already does. Define the golden digest over a canonical dump that doesn't depend on layout (entities sorted by serial, f64 values, fields as arrays), and give both the old and new layouts an adapter that writes it. Extend the scripted run beyond 600 ticks (60 s, which never reaches births, raids, construction or seasons): per-domain scenarios that use every power, plus a long run at speed 16 with a save and load in the middle.
- **high**: The generic field save loses the order of active sets, so 'save, load, run N' diverges from 'run N'.
  - Evidence: CellSet keeps cells in insertion order and `retain` keeps cells appended during iteration without visiting them (simulation/world/cell-set.ts:19-50). Fire saves the order of `burning` and `heated` explicitly (nature/fire.ts:74-80) because `tick.random.chance` draws in that order (fire.ts:332), and `#spreadHeat` writes neighbor cells in place. `sparseDifference` stores cells in ascending order (world/sparse-values.ts:8-23). The proposal's FieldDefinition has `save: "sparse"` and `hasActiveSet` but nothing that records the order. Principle 7 says 'iteration in ascending order', which changes today's order anyway.
  - Fix: Pick one. Either save the active order with each field (an Int32Array next to the sparse values), or iterate in a canonical order: ascending, over a copy of the set taken at the start of the phase, with one labeled digest bump. Write down what happens when a set changes while it is being iterated (today: cells added are kept but not visited), and test it.
- **high**: Jobs, routes, names, carried items and cached state don't fit typed columns, so saves stay lossy and replays, resync and the save/load property test can't work.
  - Evidence: society.ts:75 saves `{ ...person, job: null, mover: savedMover(person.mover, false) }`, which drops the job and the route. movement.ts:417-420 `forgetObstacles` sets scannedX/Z to +Infinity, which forces a rescan at a different tick than an uninterrupted run would. Person has `name: string`, a `carrying` object and a `weapon` object (person.ts). `Mover.path: Waypoint[]` has variable length. ThingTable has only numeric columns, and the proposal says nothing about jobs or paths. `app.resource(key, create)` has no save obligation, which is how jobs went unsaved today.
  - Fix: Every resource, component and side store must declare either `save: section` or `derive: rebuild`, where the rebuild is a pure function of saved state, and the builder refuses a declaration with neither. Add side stores keyed by handle with their own sections: a JobType registry `{kind, schema, update}` with `person.job` saved as `{kind, data}`, a pooled path store, and a string table for names. Caches that go stale over time, like nearbyObstacles, must be saved or replaced by Place queries. Land the 'save, load, run N == run N' property test in step 0 as a ratchet with a list of known failures. It must compare full canonical dumps, not just the root hash.
- **high**: Saved thing references and kind indices are never mapped by name, so a change in registry order points old references at the wrong things.
  - Evidence: ThingId = kind<<24|slot, where the kind index comes from MODULES and registry order. Handles go into Float64Array relation columns and into free-form JSON sections. Today's saved references include `PlotSpot.plant: number` (society/tribe.ts:30), `raiders.personId`/`raidId` and `relations: Map` (saved-world.ts:92-96). The walkthrough's `unitHash(context.tick, scratch.cell, id, UPROOT_SALT)` also ties randomness to the id encoding, so inserting a module earlier in MODULES changes the results.
  - Fix: Make `relation` a column type and add a `thingRef` codec to NameWriter/NameReader that writes (kind name, slot, generation) and remaps on load. Free-form sections must use that codec, never raw numbers. Add a fast-check test that shuffles every registry (kinds, tags, fields, streams, sections, systems) and checks that loading gives the same result. Key all randomness on the saved serial.
- **high**: The hasher's dirty-chunk cache isn't separated from the frame builder's change trackers. That can raise false desyncs and can also hide real ones, and the plant table would be fully rehashed every 10 ticks.
  - Evidence: Each advance, the frame builder consumes trackers: `world.groundChanges.takeRuns()`, `heightChanges.takeRegion()`, `surfaceChanges.takeRuns()`, `chronicle.takeEntries()` (simulation/frame-builder.ts:45-81). Under lockstep, peers build frames after different numbers of ticks. The proposal's setters 'mark frame rows dirty', the hasher is 'refreshed from dirty chunks' (the research suggested the existing trackers), and 'each table's columns' get no cache at all. 500k plants × ~10 columns × 4 B ≈ 20 MB, about 6–7 ms at 3 GB/s, 16 times a second at speed 16. Any write that misses a dirty mark leaves a stale chunk hash, so a real desync goes undetected.
  - Fix: Give the hasher its own dirty bits, cleared only by the hasher at fixed ticks. Add a rolling full rehash that reads 1/K of the chunks and slot blocks from raw data every tick, so every chunk is checked within K ticks whatever the dirty bits say. Cache table hashes per block of slots. In debug and CI, compare cached hashes with a full recompute. Building a frame must be a pure read with respect to state that is hashed or saved.
- **high**: Old saves store indices in an implicit order that nobody freezes, and the `formerNames` change can't remove OLDER_SAVE_PLANT_SPECIES as the proposal claims.
  - Evidence: OLDER_SAVE_PLANT_SPECIES (saved-world.ts:22-55) is the implied name table for saves written before names existed. It is not a list of renames. Grounds are saved as raw indices in terrain diffs (world-state.ts:249-254), as are plant `state`, `cropCodes`, `tribe.eraIndex` (society/tribe.ts:75) and the monument damage enum. The proposal's name list omits eras, monument damage, animal kinds, weapons, carried resources, weather kinds and power ids. Once name tables exist, lanes will feel free to reorder enums. A legacy reader that uses the current GROUNDS order would then scramble old saves without any error.
  - Fix: At the step-1 cut, freeze copies of every implicit index order inside the legacy reader and never change them. Add a column and codec type for catalog references (`catalogRef(SPECIES)`) that generates the name tables automatically, so nobody keeps a list by hand. Add a CI test that reorders each catalog and loads the fixture corpus.
- **medium**: The migration table understates the save changes, and nothing protects against stale tabs or deploy reverts.
  - Evidence: Step 5 adds 'field save sections' but lists saves as 'none'. Step 6 names legacy readers only for `society` and `vegetation`, yet it also changes the `embers`, `hazards`, `volcanoes`, `buildings` and `fauna` keys (snapshotShapeSchema, saved-world.ts:81-114). Every merge deploys, so each intermediate format reaches users. History shows how fast these flip: SAVE_VERSION was bumped and reverted the same day (b1529d2, 0675c98), and the fingerprint changed three times on 2026-10-30 (84cdfdf, 5d9d385, a9ba75d). `isLoadable: version === SAVE_VERSION` (features/saves/save-database.ts:186). A stale PWA tab that kept version 1 would load a new save and write it back without its new sections.
  - Fix: Write a legacy reader for every top-level key in today's snapshot. Add a CI ratchet on a hash of the save schema: when it changes, CI writes a fixture with main's build and commits it, so the corpus covers every format that was ever deployed. Stamp `format` and refuse to overwrite a save that is newer than the writer. Never change what a saved field means; add a new name and give it a default. Don't revert a deploy across a format change unless the reverted code has a reader for the new format.
- **medium**: The exact-math lint is scoped by path globs, so it misses shared files at module roots, and it arrives at step 10, after steps 4–9 have written new non-exact code.
  - Evidence: The GritQL scope is `core`, `simulation` and `modules/**/simulation`. The proposal puts `tornado-path.ts` ('shared by both threads') and the catalog patches in `module.ts` at the module root. Today, building the tornado path calls `Math.sin`, `Math.cos` and `Math.atan2` (simulation/powers/tornadoes.ts:73,97,101), and audio imports `tornadoPositionAt` (audio/effect-sounds.ts:2). Catalog values computed with Math.pow would differ by engine.
  - Fix: Scope the ban by what is reachable from `simulation/worker/entry.ts`, which dependency-cruiser computes, plus everything that feeds the catalog. Ship `exact-math.ts`, `unitHash` and the lint as a ratchet in step 0, so new files must comply and rewritten powers don't use non-exact math only to be converted again in step 10.
- **medium**: The lockstep and command timing model doesn't hold together.
  - Evidence: Turns are fixed at 2 ticks with commands two turns ahead. At speed 16 that is a 12.5 ms turn and a 25 ms lead, below any relay round trip. Speed and pause 'live on the main thread', but under lockstep they are shared state. §9 says the main-thread scheduler stamps ticks, while §10's protocol sends `advance { realSeconds, commands }`, which leaves the backlog and the stamping in the worker (as today, simulation.ts:503-524). StampedCommand has no sequence field. The `step()` shown always runs every phase and increments the tick, which contradicts 'a paused step applies commands without running nature'.
  - Fix: Define turns in wall time (100–200 ms) with ticks per turn = speed. Speed and pause become relay-ordered commands applied at turn boundaries. The worker (or the relay) assigns the authoritative tick and writes the replay log; the main thread never stamps. Commands carry (tick, player, sequence). While paused, the worker applies commands without advancing the tick, and the replay applies every command stamped T before tick T. Commands refer to things by handle with generation, and NOTICE carries the player.
- **medium**: Splitting rocks and monument pieces into their own kinds renumbers the plant slots that other saved state refers to.
  - Evidence: `PlotSpot.plant` (society/tribe.ts:30), the vegetation store's `burntQueuePlants: Int32Array`, and monument damage, which hashes on the plant slot (`hashToUnit(plant, damage, world.seed + ROLL_SALT)`, world/monument-damage.ts:232). The proposal mentions only 'a legacy vegetation reader'.
  - Fix: Keep plant slots as they are. Rows that move to the rock and monument tables become free slots, pushed in a fixed order, and only references to moved rows (monument conditions, hazards) are remapped, through the thingRef codec. Alternatively, keep one physical anchored table and make rock and monument kinds filters over it.
- **medium**: Gaps in the WorldBase design: a lossy encoding would break save/load equivalence, saves nobody opens stay exposed, and runtime hydrology still follows generator code.
  - Evidence: Saved diffs are taken against the full-precision generated layers (world-state.ts:249-254). The research suggests quantizing heights to Uint16, which would make a loaded world differ from the live one. Bases are attached only when an old save is opened, so a save left unopened until step 10 or terrain v2 hits 'land changed'. The fingerprint is quantized to 0.01 (generation-fingerprint.ts:25). Moving hydrology to core/world means the first terrain edit on an old world recomputes water with the new code.
  - Fix: Store the base losslessly (byte-plane shuffle plus gzip), or quantize inside the generator so the live world uses the same values. Write it at first save from the layers in memory, not at creation. After step 1 ships, attach bases to all saves in the background, and hold generator-changing PRs until then. Record `generatorVersion` and say plainly that runtime hydrology isn't frozen.
- **medium**: Resetting a section that fails to load leaves the world inconsistent, and in a network game it guarantees a desync.
  - Evidence: §9: 'A section that fails resets with a notice instead of failing the load.' If `things.person` resets, tribes, plots, raids and buildings are left pointing at people who no longer exist.
  - Fix: Sections declare what they depend on, and a failure resets the dependent sections too, or fails the load locally with a clear message. In a lockstep resync, any section failure is fatal.
- **low**: Randomness still leaks between modules through shared helpers, and the walkthrough repeats the seedless-hash bug.
  - Evidence: `Reaction.apply(context, cell)` and `things.spawn` (appearance seeds, plant rotation) would draw from whatever stream the caller's context holds, so adding a reaction shifts the draws of the ones after it. The walkthrough calls `unitHash(context.tick, scratch.cell, id, UPROOT_SALT)` with no world seed, which is the same flaw as succession.ts today. The 'unhashed effects stream' inside the simulation invites gameplay use.
  - Fix: Give each reaction its own stream, or let it use only unitHash. Make the first parameter of unitHash a branded WorldSeed so a missing seed fails typecheck. Spawn takes randomness from unitHash(serial). Move visual randomness to the main thread, keyed on presented event ids.
- **low**: Mods that are data packs can't add rules, and mods that ship code can't be held to the determinism rules.
  - Evidence: Reaction and CommandDefinition are functions (`when`, `apply`). The roadmap asks for data packs that add 'powers, species, rules', and the lint runs only on repo code.
  - Fix: Add a small declarative DSL for reactions and modifiers (field thresholds, property comparisons, a fixed set of effects) that interprets with exact operations. Keep code mods out of lockstep.
- **low**: Several fixed-size structures fail silently.
  - Evidence: Event rings overwrite when full. `AreaSummary.tagCounts` is a Uint16Array, which overflows on island-wide summaries such as lightning site picking over about 500k plants. A Uint16 generation counter combined with a LIFO free list concentrates reuse on one slot (high-churn embers), bringing back the ABA problem. Mover buckets rebuild 'at the first query of a tick', so after a teleport (grab and place, tornado fling) a query's result depends on system order.
  - Fix: Grow capacities deterministically or assert in development. Use u32 counts. Rebuild buckets at fixed phase boundaries and mark them dirty on teleport.

### Worth grafting

- Every piece of state declares either 'saved' (a section) or 'derived' (a pure rebuild from saved state), and the builder rejects a declaration with neither. The hasher digests from the save sections, so everything saved is also hashed.
- 'Save, load, run N == run N' is a property test from step 0, comparing full canonical dumps rather than root hashes, run as a ratchet with a list of known failures.
- The golden digest for refactors is a canonical dump that doesn't depend on layout (entities sorted by serial, f64 values), with long per-domain scenarios and a save and load in the middle. Every PR that changes the hash carries a label explaining the bump.
- Active sets either save their order next to the field values or iterate in a canonical ascending order over a copy taken at the start of each phase. What happens when a set changes during iteration is written down and tested.
- The hasher has its own dirty bits, separate from the frame trackers, plus a rolling full rehash of 1/K chunks and slot blocks every tick. Building a frame is a pure read.
- Persisted thing references use a `relation` column and `thingRef` codec with a name table for kinds. Randomness is keyed on a saved serial, never on ThingId or slot. A fast-check test shuffles every registry.
- Catalog references are a column and codec type (`catalogRef(X)`) that generates name tables automatically. Every implicit index order in old saves (grounds, biomes, species via OLDER_SAVE_PLANT_SPECIES, plant states, crops, eras, monument damage) is frozen in the legacy reader at the step-1 cut.
- A CI ratchet hashes the save schema; when it changes, CI writes a fixture with main's build. The fixture corpus covers every format ever deployed, and a writer refuses to overwrite a save newer than itself.
- Never change what a saved field means; add a new name with a default. That replaces version migrations.
- The exact-math lint is scoped by what is reachable from the worker entry (dependency-cruiser), and exact-math.ts with the ratchet lands in step 0, not step 10.
- Lockstep turns run in wall time with ticks per turn = speed. Speed and pause are relay-ordered commands. The worker or relay assigns ticks and writes the replay log. Commands are (tick, player, sequence) and refer to things by handle.
- Jobs, paths and names live in side stores keyed by handle (a JobType registry with `{kind, data}`), each with its own save section. Caches that go stale over time are saved or replaced by Place queries.
- The WorldBase is lossless, written at first save from memory, attached to all saves in the background after step 1, and generator-changing PRs wait until then.
- The rock and monument split keeps plant slots as they are, and only moved rows are remapped.
- When a section fails to load, its dependent sections reset too, or the load fails locally; in a network game it is fatal.
- Mods are data plus a declarative reaction DSL, so lockstep stays safe.

## Performance — 6/10

The overall direction holds up on performance. It avoids an ECS library, keeps typed-array columns with fixed capacity, keeps the per-cell plant lists, uses mover CSR buckets and block counts, and has queries write into buffers the caller owns. The tornado's context queries are not a problem: about 615 cells at the largest radius come to roughly 40–80 µs per tornado per tick, about the same as today without the allocations. The cost sits in the generic plumbing the spec puts around that core, and the design works only if those parts change.

Problems in the generic plumbing:
- `step()` builds a frame on every tick. Today one frame is built per advance of up to 40 ticks.
- It hashes whole tables every 10 ticks. I measured 7–8 ms for the plant table at 640², and it would be about 11 ms at 768². At speed 16 the budget is 6.25 ms per tick.
- Hot kernels go through generic `Fields` setters. I measured fire spread at +30% in V8 and +2.5× in JSC. The surface sweep's bit tricks can't be expressed through those setters at all.
- Exposure fields are dense, and every `CellSet` takes 5 B per cell whatever its size. Together these add up to about 64 MB of worker memory at 768², most of it empty.
- Events take object payloads, so emitting allocates, which contradicts the proposal's zero-allocation rule.
- Visitors become megamorphic. I measured 5–7× slower than inline loops.

Each of these has a local fix that leaves the architecture intact. As written, the plan would make the worker slower and larger, most of all in WebKit and on phones, which lockstep and the mobile app need.

### Strengths

- It rejects ECS libraries on measured grounds: 237 B against 16 B per entity, and 147× slower spawn and despawn. That protects the memory budget for 512k–737k plant slots (capacity is 1.25 × cells, world-generator.ts:41,271).
- Plants keep the VegetationStore SoA layout and the intrusive per-cell list. The bench on adopting the generic table is the right gate.
- The spatial backends fit the data. Mover CSR buckets rebuild in 22 µs for 5k agents and would take about 1–2 µs at today's few hundred. Per-cell lists suit anchored things, and block counts make counts within 300 m about 1000× cheaper.
- Kind capacity is fixed, so column arrays never move and systems can cache them once at build time.
- Queries use separate verbs (count, any, nearest, collect) with precompiled filters and buffers the caller owns, and distances are compared squared.
- Buildings move from full `BuildingView[]` object lists every frame to dirty-slot patches. That cuts structured-clone cost on both threads.
- Exposure fields with stateless `unitHash` chance replace today's allocating `cellsInArea` (one `AreaCell` object per cell) and the 5 linear agent scans the tornado makes each tick.
- Packages: dropping react-markdown removes a 50 kB gz chunk that is precached for every player. zod/mini saves about 37 kB gz across the main and worker chunks (measured in the packages research), and dropping comlink saves 3.9 kB in each of those chunks. Lingui adds about 10 kB gz, so the net is clearly positive.
- Exact math costs nothing for exp. I measured an fdlibm-style exp in the fire-spread loop: 1.53 ms against 1.62 ms in V8 and 0.73 ms against 0.89 ms in JSC. The determinism batch is not a performance risk for exp.

### Findings

- **high**: A frame is built on every tick. `step(kernel, commands)` ends with `return buildFrame(kernel)`, but today one frame is built per advance of up to 40 ticks. At speed 16 (160 ticks/s) that would mean about 160 frames/s instead of about 60, and a 40-tick catch-up would build 40 frames. If only the last frame were posted, the change trackers drained by the earlier builds would lose their deltas.
  - Evidence: simulation.ts:504-522 runs `step()` in a loop (MAXIMUM_TICKS_PER_ADVANCE = 40) and calls `#frameBuilder.build()` once. frame-builder.ts `build()` drains surfaceChanges, groundChanges, height and water regions and `vegetation.takeChanges()`, and copies the full burning set (`Int32Array.from(fire.burningCells())`). game-session.ts keeps one advance in flight and adds up `#pendingSeconds`, so frames already coalesce today.
  - Fix: `step()` returns void. Dirty bits, row runs, dirty slots and presented events build up across ticks. `buildFrame` runs once per advance (or per lockstep turn) and clears them. Presented events go into a per-frame buffer, not the per-tick event queues.
- **high**: Hashing every table every 10 ticks doesn't fit, which answers the proposal's own open question. The plant table alone costs 7–8 ms at 640², about 11 ms at 768², and phones are 2–4× slower. At speed 16 that is about 16 hashes per second, about 120–180 ms of worker time per second, arriving as single-tick spikes of about twice the 6.25 ms budget per tick. The `stateHash` field on every frame implies hashing is always on, even in single player.
  - Evidence: My bench, architecture/bench/ecs-perf-critic.mjs: hashing 512,000 slots × 10 words takes 7.18 ms in Node 24 and 7.95 ms in Bun on this Mac. The determinism research measured 10 field layers (16.4 MB) at 4.9 ms. VegetationStore holds about 43 B per slot (8 f32, 3 u8, cell, nextInCell).
  - Fix: Hash only in lockstep, replays and debug mode. Hash tables in pages of 1024 slots, with a dirty bit per page set by column writes, the same way fields use 64×64 chunks. Spread page refreshes over the ticks of a turn and fold one root hash per turn. Section hashes are computed on request when a desync shows up.
- **medium**: Generic `Fields` setters would go into the hottest kernels. Migration step 5 says setters replace the raw writes. Fire spread (8 neighbours per burning cell) and the surface sweep would then pay a key lookup, element kinds that differ by field, clamp, snap, an active-set check and dirty marking on every write. The surface sweep's optimisations can't be expressed through per-cell `set` at all.
  - Evidence: Measured over 20k burning cells × 8 neighbours: raw arrays 1.62 ms against generic 2.10 ms in Node (+30%), and 0.89 ms against 2.20 ms in Bun/JSC (+2.5×). WebKit parity is required for lockstep. surface.ts:142-380 sweeps 32 rows per tick, compares Uint32 bit views of snow, wetness and scorch to skip settled 32-cell segments, and calls `markRow` once per row.
  - Fix: Use two tiers. Kernels get raw arrays (`fields.f32(KEY)`) once at build time and call `activate(cell)` and `markRows(first, last)` explicitly. Generic clamping setters are only for powers, reactions and small stamped areas. Keep the golden digest so the two tiers stay equal.
- **medium**: Worker memory per cell grows by about 50%. The proposal adds dense f32 fields for molten, gust-x, gust-z, soak and acid, plus u16 germs. Every field with `hasActiveSet` gets a CellSet that costs 5 B per cell regardless of how many cells are in it. Each anchored kind gets its own per-cell list head. WorldBase keeps all 12 layers resident, against 6 today. On plant slots, the ThingTable header (live, generation, tags, variety) adds 9 B per slot. Exposure fields are empty almost all the time.
  - Evidence: Today the worker holds about 162 B per cell (66 MB at 640², 96 MB at 768²). That counts 12 terrain layers at 39 B, 8 surface fields at 32 B, canopy, occupancy, crop, disturbed and recovering at 22 B, the 6-layer generated copy at 18 B, land-areas at 29 B, navigation at 7 B, fire CellSets at 10 B and plant heads at 4 B. cell-set.ts allocates an Int32Array and a Uint8Array of cellCount each. As specified, the additions come to up to about 95 B per cell plus about 11 B per cell on plant slots: +43 MB at 640², +64 MB at 768².
  - Fix: Make CellSet a Uint32 bitset (0.125 B per cell) with a list that grows by doubling. Store exposures as sparse stamp buffers (a cell list, values, and one shared index stamped with an epoch) instead of dense fields. Use one shared per-cell head across anchored kinds, or reuse `occupancy` for buildings. For plants, reuse `species` (u8) as the variety and `state` as the tags. Keep WorldBase compressed in IndexedDB, not in worker RAM. Make step 1 measure the size.
- **medium**: Events and visitors allocate, which contradicts principle 10. `emit(key, payload)` takes an object literal, so the preallocated ring either stores references (an allocation per emit) or copies fields by reflection. The tornado example allocates an IMPACT object and a `{ visit }` closure on every tick. In a wildfire, KILLED and IGNITED per burnt plant can reach hundreds to thousands per tick.
  - Evidence: Proposal §4 Events (`emit<Payload>(key, payload: Payload)`, `read(): readonly Payload[]`) and §5 `context.things.forEach(TORNADOES, { visit: (table, slot) => ... })`. fire.ts:245-246 and 273 call `burnTreesInCell` on every cell that crosses the crown threshold.
  - Fix: Declare events with typed columns, for example `defineEvent("impact", { x: "f32", ... })`, and store them SoA. `events.push(KEY)` returns a row, and readers get column arrays plus a count. Presented events then transfer as typed arrays. Hoist visitors to module constants and enforce that with a lint rule.

- **medium**: The main-thread fire path stays as it is today, and the proposal sets no main-thread budget. The full burning set and its intensities are copied into every frame. - **low**: The claim of 'three O(blocks) calls' is wrong at tornado radii. ### Worth grafting

- `step()` returns nothing. Change state builds up across ticks, and the frame is built once per advance or lockstep turn, with a presented-event buffer per frame.
- Hash state only in lockstep, replays and debug mode. Hash tables in 1024-slot pages with dirty bits, fields in 64×64 chunks, refresh them spread over a turn, and keep one root hash per turn.
- Fields in two tiers: kernels on raw typed arrays with explicit `activate` and `markRows`, and generic clamping setters only for stamps from powers and reactions.
- A CellSet made of a Uint32 bitset plus a list that grows by doubling, instead of Int32Array and Uint8Array of cellCount, and exposures as sparse stamp buffers rather than dense fields.
- Events with typed columns stored SoA (`push` returns a row, readers get column arrays), and visitors hoisted to module constants.
- Query verbs as inline loops over compiled filters, with callbacks only for small result sets, plus a bench budget per verb.
- Anchored kinds (plants, buildings, rocks) respond only from field active sets through per-cell lists, and the generic sweeps (`expose`, `burn`, `scald`) cover movers only, checked when the registry freezes.
- Field frame encoding (`texture`, `channel`, `encode`) with a channel budget per texture checked at freeze, keeping 4-byte surface rows and the diff against the last bytes sent.
- Fire sent as ignited and extinguished deltas, and render layers with no allocation per frame and nearest-N selection through block culling.
- `fireDistance` and similar derived fields bounded by radius and refreshed at a fixed tick interval, never as a full-grid transform on every tick.
- Lockstep turn length in real milliseconds, independent of game speed.
- Tag bits assigned per kind at freeze, with compiled filters holding a mask pair per kind.
- Step 0's bench project as a CI gate with numbers: worker p95 per tick ≤6.25 ms at speed 16 on 640² with a 20k-cell wildfire and two tornadoes, run in both V8 and JSC; plant table memory within 10% of VegetationStore; main-thread frame apply ≤1 ms.
- Keep these from the proposal: no ECS library, plants in the specialised SoA store with per-cell lists, mover CSR buckets, block counts only for large radii, fixed kind capacity so column arrays can be cached, generational handles, buffers owned by the caller, and the package changes (drop react-markdown and comlink, move to zod/mini).

## Extensibility — 5/10

ECS-first is good at one kind of extension and weak at another. Adding a new source of an existing property is cheap: a second gust or heat source, a new grabbable floating kind, or a species row. Adding a new property or a new tribe system is expensive: acid, ice, germs, trade, diplomacy, beliefs, goals.

The walkthroughs undercount. A stateless power needs five central registrations; today it needs four plus POWER_GROUPS. The 25-file comparison is to the volcano, a stateful hazard, not to a comparable brush power. Several cross-module edits are hidden: tribes decisions import the sickness API, FLOATS is assumed to exist in physics, the precipitation layer needs a tint hook, and the "Barren" ground and biome don't exist.

The query model answers the tornado's four questions: dominant biome, tree counts by species, max fire and people. But it does so through closed structs in simulation/place (CellSample, AreaSummary with people, animals and buildings, fireDistance, ThingFilter.tribe). Every new module field or kind means editing core, which also breaks the proposal's own layer table.

Four gaps matter most for the roadmap:
- There is no model for variable-length or relational state, so tribes, jobs, stock, relations and territory stay unplaced, and "tribes: kind or resource?" is left open.
- There are no extension points for jobs and decisions, poses and carried items, animal brains, world layers or hydrology inputs, world rules, minimap overlays, inspector sections, metrics or goals.
- Typed records checked at compile time, plus reactions written as closures, make data-only mods impossible.
- Navigation and movement (land-areas.ts is 927 lines), chronicle, calendar and knowledge are missing from the tree.

My two scenarios each need 4–7 edits outside the new module: beavers that dam rivers, and a plague spreading through trade.

### Strengths

- Per-variety property arrays plus filters compiled at freeze time give cheap, typed answers to 'trees by species near X' (countByVariety, nearest with variety masks) without isTreeSpecies branches. The 34 hand-written kind checks really can go.
- IMPACT as one area-harm event covers the 14 damageArea quartets and fixes real coverage holes: earthquakes hurt animals, and lightning and lava reach buildings and monuments. A second hazard costs nothing in other modules.
- Kinds that drive save, frame stream, picking and grab traits remove the hand tool's per-kind edits (44 files historically) and the held-thing checks repeated in every hazard. Boats show it: no new system, and the save and stream come from the table.
- UI contributions (journalTabs, settingsSections, menuButtons, bridges), with the unions derived from them, directly fix the install panel and settings tab costs (5–7 edits each in registration.md).
- Exposure fields stamped in emit and cleared each tick, plus cell reactions on active sets, are a clean way for rain, soak and acid to douse fire without per-pair calls. Natural rain already proves the pattern (surface.ts → fire.ts:222).
- Saves keyed by name, with formerNames on the definition and looseObject sections with defaults, meet the owner's rule against per-version remaps and retire OLDER_SAVE_PLANT_SPECIES.
- Sound cues live next to their owner and the catalog is generated from files, so an orphaned cue fails knip. That fixes the 111 dead catalog lines (a2e7134, 238260c).
- Stats with explain lines give the inspector a 'why' view, which an emergent property/rule system needs for debugging.

### Worth grafting

- Five roots: core / simulation / engine / interface / modules, enforced by composite tsconfig projects per layer (noUncheckedIndexedAccess off for core/simulation/engine, on for interface).
- Module folder = module.ts (thread-safe manifest) + simulation/ engine/ interface/ sides plugged into records keyed by ModuleId; sibling modules talk only via simulation/api.ts, checked by dependency-cruiser; GritQL ban of Math.random/transcendentals/Date.now scoped to deterministic code.
- Fields declared once with lifetime (persistent | exposure), save (dense | sparse | none) and frame flags; setters own clamping, extinguish snapping, active sets and dirty rows; raw array writes disappear.
- Thing kinds as typed-array tables with generational handles (ends plot ABA), order: 'creation' to keep today's Map order and hashes, and kind-generated save sections keyed component.column with defaults and formerNames.
- Plants keep VegetationStore layout behind the same interface, gated by a bench within 10% of today's memory and spawn cost.
- Catalog values compiled to one Float32Array per property per kind, indexed by variety; rules read properties, never isTreeSpecies.
- One IMPACT area-harm event resolved against every HEALTH thing (replaces 14 damageArea call sites, gives mass-aware push).
- Spatial: per-cell intrusive lists for anchored things, CSR mover buckets rebuilt at first query per tick (22 µs at 5k), held/dead excluded in one place, squared distances, shared code with main-thread picking.
- Simulation surface is step(commands); speed/pause/backlog on the main thread; meteors as saved tasks; strokes as per-tick samples; nothing blocks saving.
- Saves: one envelope with name tables for every index-saved catalog, looseObject sections that reset with a notice, WorldBase stored once so generator changes never touch old worlds.
- Remove comlink (small typed protocol) and react-markdown/remark-gfm (privacy page as TSX).
- Walkthroughs with exact file lists (new power, new grabbable kind, tribe system with a panel) as acceptance checks for the final plan.
